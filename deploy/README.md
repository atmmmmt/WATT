# نقل المنصة إلى VPS جديد

## قبل ما تبدأ
- **الخطة المطلوبة:** VPS من نوع KVM 2 (2 vCPU / 8GB) على الأقل. خطط الاستضافة المشتركة أو "Node.js hosting" ما بتشتغل — المشروع بدّه متصفح Chrome كامل وقرص دائم.
- **قاعدة البيانات:** على MongoDB Atlas (سحابية) — ما رح ينضاع منها شي. بس غيّر كلمة مرور المستخدم من Atlas بعد النقل.
- **جلسات واتساب:** ما بتنتقل. كل رقم لازم يمسح QR من جديد مرة وحدة.
- **ملفات الوسائط القديمة** (`uploads/`) كانت على السيرفر القديم. الصور القديمة بالمحادثات رح تظهر مكسورة؛ الجديدة بتشتغل عادي.

## 1) تجهيز السيرفر
وجّه دومين الـ API (مثلاً `api.your-domain.com`) على IP السيرفر، وبعدين:

```bash
sudo bash vps-setup.sh api.your-domain.com you@example.com
```

السكربت بيركّب: Node 22، Chromium، PM2 مع تدوير السجلات، Nginx، شهادة SSL مجانية، جدار حماية، وملف swap بحجم 4GB.

## 2) رفع الكود
ارفع محتوى `apps/api` إلى `/home/waotp/api` (بدون `node_modules`)، ثم:

```bash
su - waotp
cd api
cp /path/to/env.production.example .env   # ثم عبّيه
npm ci --omit=dev
npm run build
pm2 start ecosystem.config.js
pm2 save
```

## 3) الواجهة (الداشبورد)
```bash
cd apps/dashboard
npm ci
npm run build          # الناتج في dist/
```
ارفع محتوى `dist/` على الاستضافة الثابتة أو على نفس السيرفر عبر Nginx.
`.env.production` لازم يشير لدومين الـ API الجديد:
```
VITE_API_BASE_URL=https://api.your-domain.com
```

## 4) إعادة ربط واتساب
1. على كل موبايل: واتساب ← **الأجهزة المرتبطة** ← احذف الأجهزة القديمة كلها.
   (واتساب بيسمح بـ 4 أجهزة فقط — إذا ما حذفتها رح تنقطع الجلسات.)
2. من الداشبورد: صفحة «ربط واتساب» ← امسح الـ QR لكل شركة.
3. تأكد إنه كل شركة إلها **رقم خاص فيها**. رقم واحد لأكتر من شركة = انقطاع دائم.

## 5) فحص بعد الرفع
```bash
pm2 status
pm2 logs waotp-api --lines 50
free -h                 # الرام والسواب
ps aux | grep -c chrome # عدد عمليات Chrome
```
- افتح `https://api.your-domain.com/docs`
- ابعت رسالة تجريبية من الصندوق الموحد وتأكد إنها بتوصل **مرة وحدة**

## الأداء — المتغيرات اللي بتتحكم بالاستهلاك
| المتغير | الافتراضي | شو بيعمل |
|---|---|---|
| `WA_BLOCK_PAGE_MEDIA` | `true` | يمنع تحميل الصور/الخطوط داخل Chrome (أكبر توفير للرام) |
| `WA_CHROME_HEAP_MB` | `256` | سقف ذاكرة JavaScript لكل جلسة |
| `SUPPORT_SYNC_INTERVAL_MS` | `120000` | كل قديش تتم المزامنة الاحتياطية مع واتساب |
| `TENANT_CACHE_TTL_MS` | `30000` | كاش بيانات الشركة |
| `API_KEY_CACHE_TTL_MS` | `60000` | كاش مفاتيح الـ API |
| `OTP_RETENTION_DAYS` | `0` (معطّل) | حذف تلقائي لسجلات OTP الأقدم من N يوم |
| `WA_WATCHDOG_INTERVAL_MS` | `60000` | كل قديش يتفقّد النظام إنه كل الجلسات فعلاً شغالة |
| `WA_HIBERNATE_TENANTS` | فاضي | أرقام الشركات اللي بتنام عند الخمول (OTP فقط — لا تضع شركة عندها صندوق وارد) |
| `WA_IDLE_HIBERNATE_MINUTES` | `60` | مدة الخمول قبل تحرير المتصفح |

## إعادة الاتصال التلقائي
لما تنفصل جلسة، النظام بيعيد المحاولة لحاله بفواصل متزايدة: 10 ثواني ← 30 ← دقيقة ← دقيقتين ← 5 ← 10 ← 15 دقيقة، وبيضل يحاول بلا توقف. وكل دقيقة في «حارس» بيتأكد إنه كل جلسة مفروض تكون شغالة هي فعلاً شغالة، وإذا لقى متصفح ميت بيعيد بناءه.

**الحالة الوحيدة اللي بتحتاج تدخل بشري:** إذا واتساب سجّل خروج الجهاز فعلياً (`LOGOUT` / `UNPAIRED`) — وقتها لازم QR جديد. بتشوفها بالسجلات:
```bash
pm2 logs waotp-api | grep -i "new QR scan is required"
```

**أهم سببين للانفصال المتكرر (مش مشكلة كود):**
1. **رقم واحد مربوط بأكتر من شركة** — واتساب بيسمح بـ 4 أجهزة، والخامس بيطرد الأقدم. كل شركة لازم رقم خاص فيها.
2. **موبايل الشركة ما فتح واتساب لفترة طويلة** — واتساب بيفصل الأجهزة المرتبطة إذا الموبايل الأساسي ضل بدون اتصال حوالي 14 يوم. (هاد بيفسّر انفصال كل ~15 يوم.)

**ملاحظتان:**
- إلغاء مفتاح API بياخد مفعوله خلال دقيقة (بسبب الكاش).
- تعديل قوالب OTP بيظهر خلال 30 ثانية (بسبب كاش الشركة).

## كم شركة بيتحمّل السيرفر
| الخطة | قبل التحسينات | بعدها (تقديري) |
|---|---|---|
| KVM 1 (4GB) | 2–4 | 4–6 |
| KVM 2 (8GB) | 8–12 | **15–20** |
| KVM 4 (16GB) | 20–28 | 35–45 |

الأرقام تقديرية — قِسها فعلياً بـ `free -h` بعد ما توصل لـ 5 شركات متصلة.
